# Notes in /v3/quote Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/v3/quote?footnotes=none|markers|full` returns the notes anchored to the verses of the response, to `reader`-scope keys only.

**Architecture:** After the quote pipeline has filled `$ctx->results`, `QuoteHandler` asks a `NoteRepository` for the anchors of each (edition, book, chapter range) in the results, matches them to rows by verse identity in PHP, and, for `full`, loads the bodies and citations of the notes it kept. Nothing runs when `footnotes` is absent or `none`, so those responses are unchanged.

**Tech Stack:** PHP 8.4, PDO/PostgreSQL, PHPUnit 13 integration tests (synthetic notes on the `TEST1` edition).

**Spec:** `docs/superpowers/specs/2026-11-23-footnotes-design.md` (Part 3).

## Global Constraints

- Default `none`: a request without `footnotes` (or with `none`) gets exactly today's response; no query on the note tables.
- Values other than `none|markers|full` → 400 (`ValidationException`).
- `markers`/`full` without a credential of scope `reader` → 403 (`ForbiddenException`), detail: "Notes are available only with the BibleGet website's reader key."
- `markers`/`full` with `return=xml|html` (or an XML/HTML Accept) → 400, detail: "Notes are available in JSON only."
- Order of checks: value, then credential, then format.
- Only notes anchored to verses in the response; a note appears with the verse where it begins.
- Match anchors to rows by identity: `book` (universal number, `univbooknum`), `chapter`, `verse`, `verse_segment`, `text_tradition`, `printed_chapter`, NULLs equal (as `<T>_identity`, NULLS NOT DISTINCT).
- No copyrighted text in this repository: tests insert synthetic notes.

## Shapes (rulings within the spec's sketch)

- Note id: `"{EDITION}:{source_id}"` (stable across re-imports, unique across editions in a multi-version response; the serial `note.id` is not).
- `markers`: every row gains `notes: [{id, kind, marker, field, position}]`, `[]` when none; ordered by field (`chapter`, `title1`, `title2`, `title3`, `text`), then position (NULL, the verse as a whole, first), then marker.
- `full`: the same rows, plus a top-level `notes: {id: {kind, marker, label, title, body, refs: [{start, end, span}]}}` (an empty JSON object when none), each note once. `start` = `{book, chapter, verse, segment, printed_chapter}` (verse NULL for a whole chapter), `end` = `{book, chapter, verse}` or NULL, `span` = `[span_start, span_end]`; refs ordered by `ord`.

## Review Focus

- A row with `verse_segment`/`text_tradition` NULL must match an anchor with NULLs, and not one with `'a'`/`'GREEK'` (Esther). (Test `anchorsMatchByIdentityIncludingNulls`.)
- Two versions in one request: each row gets only its own edition's notes. (Test `eachEditionGetsItsOwnNotes`.)
- A whole-verse anchor (position NULL) is returned as `position: null`, first in its field. (Test `markersAreOrderedByFieldThenPosition`.)
- A note with two anchors in the response appears once in `full`'s map. (Test `fullListsEachNoteOnce`.)
- `footnotes=none` and absent: no `notes` key anywhere. (Test `withoutTheParameterNothingChanges`.)
